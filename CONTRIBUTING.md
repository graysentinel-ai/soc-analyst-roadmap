
# Contributing to the GraySentinel SOC Analyst Roadmap

Thank you for your interest in contributing to the GraySentinel SOC Analyst Roadmap.

This repository is built around one principle:

**Proof Over Certificates.**

We believe cybersecurity skills should be developed through practical work, clear documentation, responsible experimentation and verifiable evidence.

Contributors help us improve learning resources, practical exercises, defensive security examples and technical documentation.

Every contribution should make the repository more accurate, useful, understandable or practical.

---

# 1. What You Can Contribute

We welcome relevant contributions in the following areas.

## Documentation

- Improve explanations of cybersecurity concepts.
- Correct technical inaccuracies.
- Improve learning instructions.
- Add beginner-friendly examples.
- Improve grammar, readability and structure.
- Add references to official documentation.

## Learning Modules

- Improve existing module content.
- Suggest missing foundational topics.
- Add practical learning exercises.
- Create structured revision notes.
- Improve learning objectives and completion checks.

## Labs and Practical Exercises

- Create safe, isolated lab scenarios.
- Improve existing exercise instructions.
- Add synthetic datasets.
- Add investigation worksheets.
- Document expected outputs.
- Provide reproducible testing steps.

## Detection Engineering

- Contribute defensive detection examples.
- Improve Sigma rule documentation.
- Add synthetic test events.
- Explain detection logic.
- Document false-positive considerations.
- Improve rule validation instructions.

## Projects and Portfolio Resources

- Suggest practical SOC projects.
- Improve report templates.
- Add evidence documentation formats.
- Create investigation checklists.
- Improve portfolio presentation guidance.

## Quality Assurance

- Identify broken links.
- Report documentation errors.
- Test instructions in a safe environment.
- Identify inconsistent terminology.
- Suggest accessibility and usability improvements.

# 2. Before You Start

Before contributing:

1. Read this document.
2. Read the repository README.
3. Review the relevant module or resource.
4. Check whether the issue or improvement already exists.
5. Understand the scope of your proposed change.
6. Follow the repository's security and attribution requirements.

If you are unsure whether a contribution is suitable, open an issue and describe your proposal before preparing a large change.

---

# 3. Contribution Workflow

Follow this process for every contribution.

## Step 1: Identify an Improvement

Choose a specific issue, missing explanation, documentation error, lab improvement or practical exercise.

Avoid submitting unrelated changes in a single contribution.

## Step 2: Discuss Major Changes

For substantial changes, open an issue first.

Include:

- What needs improvement?
- Why is the change useful?
- Which file or module is affected?
- What evidence supports the proposed change?
- Are there any safety or compatibility considerations?

Small spelling corrections and clearly isolated documentation fixes may be submitted directly.

## Step 3: Prepare Your Work

- Work on the relevant files only.
- Follow the existing repository structure.
- Use clear filenames.
- Keep explanations technically accurate.
- Add references where appropriate.
- Avoid unnecessary dependencies.
- Do not include secrets or personal information.

## Step 4: Validate Your Contribution

Before submitting:

- Review your changes.
- Check Markdown formatting.
- Verify external links.
- Test commands and examples where applicable.
- Confirm that lab instructions work in the documented environment.
- Remove sensitive information.
- Confirm that the contribution follows the security requirements.

Do not claim that an exercise or detection rule has been tested if it has not been tested.

## Step 5: Submit a Pull Request

Your pull request should explain:

- What changed?
- Why was it changed?
- Which files were affected?
- How was it validated?
- Are there known limitations?
- Are external resources or references included?

Provide screenshots, sample outputs or test evidence when they materially help reviewers.

## Step 6: Review and Feedback

GraySentinel maintainers may:

- Approve the contribution.
- Request changes.
- Ask for technical clarification.
- Suggest a different implementation.
- Decline the contribution.

A submitted pull request is not automatically accepted.

# 4. Technical Contribution Standards

All technical contributions should meet the following standards.

## Accuracy

- Verify technical statements.
- Prefer official documentation and primary references.
- Clearly identify assumptions.
- Avoid unsupported security claims.
- Distinguish observations from conclusions.

## Reproducibility

Where applicable, include:

- Required environment.
- Prerequisites.
- Setup instructions.
- Execution steps.
- Expected results.
- Validation method.
- Known limitations.

## Documentation

Write for the intended learner.

A beginner should be able to understand the purpose of an exercise before attempting it.

Explain why a command or technique is being used, not just what to type.

## Code Quality

- Keep code readable.
- Use meaningful names.
- Include comments where they improve understanding.
- Avoid unnecessary complexity.
- Document dependencies.
- Do not include hardcoded credentials, tokens or secrets.

## Evidence Quality

Evidence should support the work being described.

Examples include:

- Relevant screenshots.
- Sanitised log excerpts.
- Test outputs.
- Sample datasets.
- Reproducible steps.
- Technical explanations.

Do not submit fabricated results or screenshots from work you did not perform.

# 5. Cybersecurity Safety Requirements

This repository is intended for responsible cybersecurity education and defensive capability development.

All contributions must comply with applicable laws, authorisation requirements and responsible security practices.

## Allowed Contributions

- Defensive security documentation.
- Synthetic log datasets.
- Local lab exercises.
- Detection engineering examples.
- Incident investigation scenarios.
- Secure configuration guidance.
- Authorised testing instructions.
- Educational demonstrations in controlled environments.

## Prohibited Contributions

Do not submit:

- Instructions for unauthorised access to real systems.
- Stolen credentials or access tokens.
- Malware intended for real-world deployment.
- Unauthorised exploitation of third-party systems.
- Private customer or employee information.
- Confidential company logs or internal documents.
- Data collected without permission.
- Content intended to facilitate credential theft, destructive activity or unlawful access.

## Lab Safety

Every lab must clearly describe its intended environment and scope.

Use:

- Local virtual machines.
- Isolated networks.
- Synthetic datasets.
- Intentionally vulnerable training environments.
- Systems for which explicit authorisation exists.

Never assume that a publicly accessible system is authorised for testing.

GraySentinel maintainers may reject or remove content that creates unacceptable safety or legal risks.

# 6. Attribution and Originality

Contributors must submit original work or work they are legally permitted to share.

When using external material:

- Identify the original source.
- Provide the source link.
- Follow the applicable licence.
- Preserve required attribution.
- Clearly distinguish original content from adapted material.

Do not copy another person's article, repository, lab, report or research and present it as your own.

Do not submit AI-generated content as verified technical work without reviewing, validating and understanding it.

AI tools may assist with drafting, coding and research. The contributor remains responsible for the accuracy, originality, safety and licensing of the submitted work.

Maintainers evaluate contributions based on relevant factors, including:

# 10. Pull Request Guidelines

Use a descriptive pull request title.

Examples:

- `docs: improve networking fundamentals`
- `lab: add authentication log investigation`
- `detection: add a tested Sigma example`
- `fix: correct Windows event reference`
- `docs: improve incident report template`

A useful pull request description should contain:

### Summary

Briefly explain the proposed change.

### Motivation

Explain the problem or learning gap being addressed.

### Changes

List the important files and modifications.

### Validation

Explain what was checked or tested.

### Evidence

Attach relevant outputs or screenshots when useful.

### Limitations

Mention anything that remains untested or incomplete.

# 11. Reporting Security Issues

Do not publish sensitive vulnerability details, credentials or exploit information in public issues or pull requests.

For security concerns, follow the instructions in [SECURITY.md](SECURITY.md).

Provide enough information for the maintainers to understand the concern without unnecessarily exposing sensitive information.
