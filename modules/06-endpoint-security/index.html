1. Learning objectives

By the end of this module, you should be able to:

  • Explain the role of endpoint security in an organisation.
  • Identify common endpoint threats and attack surfaces.
  • Describe practical operating system hardening controls.
  • Differentiate antivirus, EDR and XDR.
  • Interpret process, authentication and endpoint alert records.
  • Identify suspicious patterns that require investigation.
  • Document an endpoint incident with evidence and limitations.
Core principle: An endpoint alert is a lead for investigation, not automatic proof of compromise. Validate the process, user, host, parent process, timing and surrounding activity.

2. Endpoint security fundamentals

An endpoint is a device that connects to a network and runs applications or services. Examples include employee laptops, workstations, servers and virtual machines.

Endpoint protection

Controls that reduce the risk of malware, unauthorised access and misuse.

Hardening

Reducing unnecessary services, permissions, software and attack surface.

Telemetry

Recorded information about processes, users, files, connections and events.

Detection

Identifying activity that may violate security policy or indicate a threat.

Containment

Limiting the spread or impact of a confirmed or suspected incident.

Recovery

Restoring systems safely and verifying that required controls work.

Endpoint security objectives

  • Protect data stored or processed on devices.
  • Control access to operating systems and applications.
  • Reduce exposure to malicious files and processes.
  • Monitor activity that may indicate compromise.
  • Support investigation and recovery when incidents occur.

Many legitimate administrative tools can also be misused. A tool name alone is not enough to classify activity as malicious. Investigate execution context, ownership, authorisation and behaviour.

4. Endpoint hardening

Hardening reduces unnecessary exposure before an incident occurs. It should be based on the device's role and approved organisational policy.

ControlPurposeEvidence to review
Patch managementAddress known software vulnerabilitiesPatch status and update records
Least privilegeLimit unnecessary administrative accessLocal group and role membership
Disk encryptionProtect data stored on a deviceEncryption policy and device status
Application controlRestrict unapproved software executionAllowlist or application control policy
Host firewallControl inbound and outbound device trafficFirewall policy and event records
Secure configurationDisable unnecessary features and insecure settingsConfiguration baseline and compliance results
Endpoint monitoringRecord activity and support detectionAgent health and telemetry coverage
Backup and recoveryRestore data and services after disruptionBackup status and restore-test evidence

Example hardening review checklist

  • Is the operating system supported and patched?
  • Are local administrator permissions justified?
  • Is disk encryption enabled where required?
  • Are unnecessary services disabled?
  • Is endpoint protection installed and reporting?
  • Are host firewall rules aligned with device purpose?
  • Are backups available and restore tests documented?
  • Are security events forwarded to the appropriate monitoring platform?

5. Antivirus, EDR and XDR

Antivirus (AV)

Primarily identifies and blocks known or suspicious malicious files and activity using detection methods that vary by product.

Endpoint Detection and Response (EDR)

Collects endpoint telemetry and supports investigation, detection and response actions.

Extended Detection and Response (XDR)

Correlates security information across multiple domains such as endpoints, identity, email and network systems.

Security Information and Event Management (SIEM)

Centralises and analyses security events from multiple sources to support monitoring and investigation.

Comparison

CapabilityAVEDRXDR
Malware detectionCore capabilityCommon capabilityMay incorporate endpoint detections
Endpoint telemetryVariesCore capabilityUsually integrated from endpoint sources
Investigation timelineLimited or product-dependentCommon capabilityCross-domain correlation
Response actionsProduct-dependentCommon capabilityProduct-dependent, often cross-domain
Multiple security domainsNot its primary focusEndpoint-focusedCore focus
Product capabilities differ. These are conceptual distinctions, not guarantees about every vendor or deployment.

6. Endpoint telemetry and suspicious indicators

Endpoint telemetry records what happens on a device. Analysts use these records to reconstruct process execution, account activity, file changes and network communication.

Telemetry typeUseful fieldsInvestigation question
Process creationProcess name, path, user, parent process, command lineWhat launched the process and why?
AuthenticationUser, logon type, source, result, timestampWas access expected?
File activityPath, hash, operation, process, timestampWas an unusual file created or modified?
Service activityService name, account, binary path, statusWas a service installed or changed unexpectedly?
Scheduled tasksTask name, trigger, action, creatorWas an unexpected recurring task created?
Network connectionsProcess, local and remote address, port, protocolWhich process communicated with which destination?

Patterns that deserve investigation

  • A process running from an unusual directory.
  • An unexpected parent-child process relationship.
  • A new service or scheduled task without an approved change.
  • Unusual privilege changes or administrative activity.
  • A process making unexpected outbound connections.
  • Endpoint protection becoming disabled or unhealthy.
  • Unexpected changes to security configuration.
These are investigation leads, not definitive indicators of compromise. Validate software ownership, signatures, change approvals, normal device behaviour and supporting telemetry.

10. Endpoint incident response basics

Incident response should follow the organisation's approved process. Actions that affect production systems must be performed by authorised personnel with appropriate approvals.

  1. Prepare: Define roles, tools, escalation paths and response procedures.
  2. Identify: Validate the alert and establish the affected device, account and scope.
  3. Preserve: Protect relevant logs and evidence, recording collection details.
  4. Contain: Apply approved measures to limit impact or spread.
  5. Eradicate: Remove confirmed causes and address the weakness.
  6. Recover: Restore the endpoint safely and validate its security state.
  7. Review: Document lessons, control gaps and preventive improvements.
Isolation, shutdown, memory collection and evidence acquisition can affect volatile data or business operations. Follow the incident response plan and obtain the required approval before acting.

11. Endpoint investigation report

Your report should clearly separate recorded facts from your assessment.

  1. Case summary: What triggered the investigation?
  2. Scope: Device, account, time range and systems involved.
  3. Data sources: Endpoint alerts, process records, authentication and network events.
  4. Method: Filters, queries and review steps.
  5. Timeline: Relevant activity in chronological order.
  6. Findings: Observations supported by evidence.
  7. Assessment: Interpretation, severity and confidence.
  8. Limitations: Missing records, telemetry gaps or unavailable context.
  9. Recommendations: Authorised response and remediation steps.
  10. Evidence references: File names, hashes where appropriate and record identifiers.

Example finding

Observation:
A synthetic endpoint record shows a file created in the user's
Downloads directory, followed by process execution and an outbound
connection associated with that process.

Assessment:
The sequence deserves investigation. The records alone do not
establish whether the file is malicious or whether the activity
was authorised.

Next checks:
Validate file provenance, hash, signature, parent process,
endpoint detection details, user context and network destination.
