Log Analysis

Learn how to read system and security logs, recognise unusual activity, connect related events, and turn raw records into an evidence-based investigation.

Level: Beginner to Intermediate Focus: Defensive Security Practice: Synthetic Logs Evidence: Investigation Report

In this module

1. Learning objectives

By the end of this module, you should be able to:

  • Explain what logs are and why security teams investigate them.
  • Identify common operating system, authentication, network and application log sources.
  • Read timestamps, event types, source addresses, usernames and outcomes.
  • Filter records to investigate a defined question.
  • Recognise patterns that may indicate suspicious activity.
  • Correlate multiple events into a defensible timeline.
  • Document findings, limitations and recommended next steps.
Core principle: A log entry is an observation, not a verdict. Investigators need context and corroborating evidence before concluding that an event represents an attack.

2. Log analysis fundamentals

A log is a time-stamped record generated by a system, application, network device or security tool. Logs help analysts reconstruct what happened and when.

Event

A recorded occurrence, such as a user login or service restart.

Log source

The system or application that generated the record.

Timestamp

The recorded time of an event. Time zone and clock accuracy matter.

Event context

Related details such as user, host, source IP, process or result.

Correlation

Connecting multiple records using time, identity, host or other fields.

Timeline

A chronological sequence of relevant observations and findings.

Common log fields

FieldMeaningInvestigation use
timestampWhen the event was recordedBuild a timeline and compare events
hostnameSystem that generated the eventIdentify the affected endpoint or server
usernameAccount associated with the eventTrace account activity
source_ipOrigin address recorded by the sourceGroup activity by source
event_typeKind of recorded activityFilter relevant activity
statusOutcome such as success or failureCompare failed and successful actions
processProcess associated with the eventInvestigate process execution
messageHuman-readable event detailsUnderstand the recorded action

Raw logs and structured logs

Raw logs may be plain text with inconsistent formats. Structured logs organise information into predictable fields, often using JSON or key-value pairs. Structured fields make filtering and correlation easier. 

{
  "timestamp": "2026-10-14T09:15:22Z",
  "hostname": "workstation-07",
  "username": "analyst01",
  "event_type": "authentication",
  "source_ip": "192.0.2.45",
  "status": "failure",
  "message": "Invalid password"
}
Time matters: Do not assume every system uses the same time zone or has a correctly synchronised clock. Record the time zone, source and any known clock offset before building a timeline.

3. Common log sources

SourceExamples of recorded activityQuestions to investigate
Windows Event Logs Logons, account changes, services, process-related events Which account logged in? Was access successful?
Linux authentication logs SSH attempts, authentication outcomes, privilege use Were there repeated failures or unexpected access?
Web server logs HTTP requests, response codes, requested paths, client addresses Were sensitive paths accessed or unusual requests made?
Firewall logs Allowed or denied connections, source and destination details Was unexpected network traffic recorded?
DNS logs Domain queries and responses Were unusual domains queried?
Endpoint security logs Alerts, detections, process and file activity What triggered the alert and what evidence supports it?
Cloud audit logs Sign-ins, API calls, resource and permission changes Who changed a resource or permission, and when?

Different products use different event identifiers and field names. Learn to interpret the source documentation rather than assuming one event ID means the same thing everywhere.

4. A repeatable investigation workflow

  1. Define the question. State what you are trying to establish.
  2. Identify the source. Record which systems and log files are available.
  3. Preserve the evidence. Keep original files unchanged and work on copies.
  4. Check time context. Record time zone, clock accuracy and relevant time range.
  5. Filter the data. Narrow by user, host, source, event type or time.
  6. Find patterns. Look for unusual sequences, frequency, timing and outcomes.
  7. Correlate events. Compare relevant records across available sources.
  8. Build a timeline. Put observations in chronological order.
  9. State findings carefully. Separate facts, interpretations and unknowns.
  10. Recommend next steps. Identify what should be checked or contained by an authorised team.
Evidence discipline: Preserve the original log, record the file name and collection time, and document any filtering or transformation. Do not silently discard records that contradict an initial theory.

5. Patterns worth investigating

These patterns can justify further investigation. None proves malicious activity by itself.

PatternWhat you might observeWhat to validate
Repeated authentication failures Many failed logins for one or more accounts Source, frequency, affected accounts and normal user behaviour
Failure followed by success Several failed attempts followed by a successful login Whether the successful session is expected and authorised
Unusual login time Authentication outside a user's normal pattern Shift schedules, travel, automation and time-zone context
Unexpected privilege change Account added to a privileged group or role Change request, actor, approval and business reason
Unusual web requests Repeated requests to sensitive or unexpected paths HTTP status, request context, application behaviour and source
Unexpected outbound activity Connection to an unusual destination Asset role, approved services, DNS and firewall context

Useful analysis concepts

  • Frequency: How often does an event occur?
  • Baseline: What is normal for this user, host or service?
  • Sequence: What happened immediately before and after?
  • Scope: How many accounts, systems or services are involved?
  • Confidence: How strongly does the available evidence support the conclusion?

Investigation exercise Work with the synthetic authentication records below. Identify repeated failures and determine whether a later successful login needs further review.

Scenario: Unusual account activity Synthetic dataset · UTC

An internal monitoring alert reports repeated failed authentication attempts against the account analyst01. Your task is to inspect the records and describe what they show.


Investigation questions

  1. How many failed attempts are recorded for analyst01?
  2. Which source address appears in those failed attempts?
  3. Is there a successful login after the failures?
  4. What additional evidence would you request before concluding that the account was compromised?

7. Practical Lab 2: Event correlation and timeline

A single log source rarely tells the whole story. In this exercise, compare authentication, account-management and endpoint observations.

Scenario: Account activity followed by a configuration change Synthetic dataset · UTC 
2026-10-14T09:14:02Z AUTH host=WS-07 user=analyst01 status=failure src=192.0.2.45
2026-10-14T09:14:18Z AUTH host=WS-07 user=analyst01 status=failure src=192.0.2.45
2026-10-14T09:14:41Z AUTH host=WS-07 user=analyst01 status=success src=192.0.2.45
2026-10-14T09:19:05Z ACCOUNT host=WS-07 actor=analyst01 action=group_change target=ops-admin
2026-10-14T09:22:10Z ENDPOINT host=WS-07 event=process_start name=admin_tool.exe user=analyst01
2026-10-14T09:25:33Z AUTH host=WS-07 user=analyst01 status=success src=192.0.2.45

Your analysis

  1. Put the six events in chronological order.
  2. Identify the sequence that deserves the highest priority for review.
  3. Which event records an account or group change?
  4. What would you verify about admin_tool.exe?
  5. What evidence is missing before you can confirm unauthorised activity?
The records show a sequence that deserves investigation. They do not establish that the account was compromised or that the tool was malicious. Validate the change approval, process details and session context.

Questions

  1. Which requests returned an authentication or access-related error?
  2. What does HTTP 401 generally indicate?
  3. What does HTTP 403 generally indicate?
  4. Why should the final dashboard request be checked in context?
  5. What application-side logs would help confirm what happened?

Remember: an HTTP status code describes the server's response. It does not independently establish the intent of the requester.

9. Build an investigation report

Your report should allow another analyst to understand what you checked, what you found and what remains unknown.

Recommended report structure

  1. Case summary: A short description of the investigation question.
  2. Scope: Systems, accounts, data sources and time range reviewed.
  3. Method: Filters, queries and analysis steps used.
  4. Observations: Facts directly supported by the records.
  5. Timeline: Relevant events in chronological order.
  6. Assessment: Your interpretation and confidence level.
  7. Limitations: Missing logs, clock uncertainty or unavailable context.
  8. Recommendations: Specific next checks or authorised response actions.
  9. Evidence references: File names, record identifiers and supporting extracts.
Writing rule: Use phrases such as “the logs show” for observations and “this may indicate” for interpretations. Avoid declaring an account compromised unless the evidence supports that conclusion.

Example finding

Observation:
Three failed authentication attempts were recorded for analyst01
from 192.0.2.45, followed by a successful authentication.

Interpretation:
The sequence may indicate repeated password guessing or a user
entering an incorrect password. The available records do not
establish which explanation is correct.

Next checks:
Review session details, MFA records, endpoint telemetry, account
owner confirmation and any related access events.
